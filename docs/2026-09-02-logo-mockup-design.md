## 1. 概述

### 1.1 业务背景

包类定制业务，客户下订单后需要把客户 logo 印到包上。手上有：包的正视图照片（棚拍白底平正图）+ 客户 logo 矢量源文件。

现有做法：设计师在 Illustrator 里手工排，一个订单 1 小时以上。

### 1.2 三份交付物

| # | 交付物 | 给谁 | 内容 | 格式 |
|---|--------|------|------|------|
| 1 | 客户选款图 | 客户 | 3～5 个方案拼一张，客户圈选回编号 | PNG |
| 2 | 工艺尺寸图 | 贴片厂 | 1:1 矢量 + 尺寸链 + 外框 + 色号（选填），文字已转曲，打印可量 | **PDF（主）/ SVG** |
| 3 | 定位图 | 包厂 | 包正视图 + logo 外框 + 距基准边的尺寸链 | PDF / SVG |

**三份同源**：客户在方案 B 上画个圈，后两份的毫米数即已确定，不需要人工二次换算。这是整件事值不值得做的关键。

### 1.3 核心约束（不可违反）

**S1 效果图必须走程序化合成，不能用生成式 AI。**

市面上一票 AI mockup 工具（底层 Nano Banana / Gemini / Seedream）宣传"自动识别曲面、自动匹配光影"，但对本场景是错的：它是**重新生成一张图**，logo 的长宽比、笔画、颜色、位置都可能被模型微调。后果是客户选定了"这个大小这个位置"，却**没法反推真实尺寸**，下游 S2、S3 全部断链。

合成方式锁定为：**平铺叠加**（alpha 合成）。不做正片叠底、不做网格变形、不做光影模拟。Joe 已确认此选项。

**S2 全链路每个数字必须可复现、可追溯。**

由此推出：**边界框不使用 AI 视觉识别**（详见 6.3）。`px_per_mm` 从框算出，框的不确定性会直接污染所有下游毫米数。

### 1.4 成功标准

| 指标 | 现状 | 目标 |
|------|------|------|
| 单订单耗时 | AI 手工 1 小时以上 | 5～10 分钟 |
| 尺寸误差 | 手工量取 | 参数驱动，零换算误差 |
| 改稿成本 | 从头排一遍 | 改 project.json 一个数，重新导出 |

### 2.2 我替 Joe 定的默认值（可推翻）

1. **后端用 FastAPI**（pip 装 fastapi + uvicorn + python-multipart），不用 Python 标准库。理由：要处理文件上传，标准库手写 multipart 解析容易出 bug。
2. **前端用原生 HTML/CSS/JS**，不引入 React/Vue，**但强制分层**：
   - `state.js`：单一数据源。框坐标、`px_per_mm`、方案数值只存在此处，任何模块不得自行缓存
   - `canvas.js`：只管绘制与交互（画框、拖拽、缩放、命中检测），不持有业务数据
   - 侧边栏订阅 `state` 变化重绘，不反向写数据
   理由：界面主体是 Canvas 而非 DOM，框架的 diff 机制对画布内容无效；分层的真正目的是**保留可迁移性**——将来若上 React/Vue，只需把 `state.js` 换成 `useReducer`，Canvas 代码几乎不用动。Joe 2026-09-03 确认
3. **中间处理全部操作 SVG 文本**，不引入矢量图形库。SVG 就是 XML，缩放和加标注是字符串拼接。
4. **四角控制点锁长宽比**，按住 Shift 才自由拉伸。理由：logo 变形是低级事故。
5. **输出格式锁定 PDF（主）+ SVG。EPS 砍掉，`.ai` 已确认无法实现。**
   实测依据（2026-09-03）：
   - `.ai` —— Inkscape 1.4.4 不支持导出，允许值列表中根本没有（专有格式无公开规范，详见探测报告 7.1）
   - `EPS` —— ① 我们自己读不了（Inkscape 1.4 导入报 parser error），交付一个无法自检的格式有风险 ② 实测 EPS BoundingBox 按**内容边界**计算而非页面（页面 115.30×95.00mm，BoundingBox 仅 86.78×69.85mm），与"1:1 打印可量"的语义不符
   - `PDF` —— **已全链路验证通过**：尺寸偏差 0.000003mm、文字已转曲、纯矢量、Joe 用 Adobe Illustrator 实机确认路径可编辑。且 PDF 是印前交付国际标准（PDF/X），工厂标准收件格式就是它
   - 格式列表在代码中仍做成**配置项**，将来若贴片厂坚持要其他格式，只改配置不改代码
6. **色号改为选填**（PANTONE 或 CMYK）。填写则标在工艺尺寸图上给贴片厂；留空则不标该行，且**不阻断导出**。
   注意区分两个概念：**「改色功能」不做**（把客户 logo 从红改成蓝这类需求不存在），**「色号标注」保留**（贴片厂需要知道印什么色）。色号在此仅作信息通道，不做强制校验。Joe 2026-09-03 确认
7. **框形状 v1 只用矩形**。理由：斜边无法标尺寸链；可印区 99% 是矩形；异形可用多个矩形组合覆盖。Joe 2026-09-03 确认
8. **框带可选命名 / 备注字段**。理由：旧语义模型里"翻盖"这类名字会印在定位图上告诉包厂参照哪，新模型不能丢这层信息。
9. **产品框只框包主体，提手 / 肩带 / 织带不计入**。理由：这些部件伸出主体且形状不定，计入会污染比例尺。UI 需明示此规则。
10. **支持多个 logo 框（数组）**，UI 默认只画一个。理由：成本为零，不封死多 logo 场景。

## 3. 架构

```
┌─ 浏览器界面（原生 HTML/CSS/JS + Canvas）──────────┐
│  上传 → 标定 → 拖动缩放 → 导出                     │
└──────────────┬─────────────────────────────────┘
               │ HTTP localhost
┌──────────────▼─────────────────────────────────┐
│  Python 本地服务（FastAPI）                      │
│  ├─ 参数管理      project.json 读写              │
│  ├─ 预览合成      Pillow（alpha 平铺叠加）        │
│  ├─ 导出编排      串起三份交付物                  │
│  ├─ 工艺尺寸图生成  SVG 文本模板                  │
│  ├─ 定位图生成      SVG 文本模板                  │
│  └─ 引擎适配层 ★   隔离 Inkscape，可整体替换      │
└──────────────┬─────────────────────────────────┘
               │ subprocess
┌──────────────▼─────────────────────────────────┐
│  Inkscape CLI                                   │
│  ai/pdf/svg → SVG        SVG → pdf/png          │
└────────────────────────────────────────────────┘
```

**★ 引擎适配层是这套设计里唯一为将来留的口子。** Inkscape 被关在这一层内，上层完全不知道它存在。将来若需换成 AI COM 或加兜底引擎，只改这一个文件，上层逻辑一行不动。

**明确不做的模块**：背景分割 / 包身识别。经复核，三份交付物无一需要包的像素包围盒（客户选款图用整图、工艺尺寸图与包图无关、定位图只需包图 + 框 + 尺寸链）。原 v0.1 为此预留的工作量归零。

### 3.1 为什么选 Inkscape 而不是 AI COM

| | Inkscape | AI COM | 纯 Python 矢量栈 |
|---|---|---|---|
| 保真度 | 高（AI 特有高级效果可能丢） | 最高 | 中 |
| 速度 | 无头，1～2 秒 | 启动 AI 10～30 秒，常驻吃 1～2GB 内存 | 最快 |
| 稳定性 | 高，职责窄 | 中，依赖 AI 版本 | 高，但自研转换层代码量大 |
| 新增依赖 | Inkscape（免费） | 无（已有 AI） | pip 装 pymupdf |

Inkscape 只干两件事（输入转 SVG、输出转 PDF/PNG），职责窄到可以随时换掉，这最符合"稳定优先"。

### 3.2 项目文件夹结构

```
projects/
  2026-09-03_<客户>_<包型>/
    project.json        所有参数，可复现可回退
    input/
      bag.jpg           包正视图
      logo.ai           客户源文件
      logo.svg          Inkscape 转出的中间格式
      logo_preview.png  前端预览用
    output/
      selection.png     客户选款图
      spec.ai / .pdf / .eps / .svg
      placement.pdf / .svg
```

一个订单 = 一个文件夹。`project.json` 存全部参数，客户改主意时改一个数重新导出即可。

## 4. 界面

主界面分三栏 + 顶部步骤条 + 底部方案条。

**顶部**：项目名 + `1 上传 › 2A 产品框 › 2B logo 框 › 3 摆放 › 4 导出`

### 步骤 1 上传

左栏显示已上传的包图与 logo 文件名。

### 步骤 2A 产品框（定比例尺）

- 中栏显示包图，用户拖出一个矩形贴合**包主体**轮廓
- **界面需明示规则**：只框包主体，提手 / 肩带 / 织带不计入
- 右栏输入：**实物宽度 mm（必填）**、实物高度 mm（选填）
- 系统算 `px_per_mm = 产品框宽px ÷ 实物宽mm`，实时显示
- 若填了高度：显示「推算高 vs 填入高」的差值，**黄色信息条，不阻断**（见 7 节）
- 提供**放大精贴**视图，便于精确贴边

### 步骤 2B logo 框（定基准 + 安全区）

- 中栏在包图上再拖一个矩形，即**可印区**
- **硬约束：框的每一条边必须落在包身肉眼可辨的物理特征上**（翻盖边、前袋边、包身边、缝线）。界面需提示此规则
- 右栏：**框命名 / 备注**（选填，如"翻盖可印区"）
- 同样提供放大精贴视图

### 步骤 3 摆放

- 中栏：包图 + logo 框（虚线）+ logo 叠加
- logo **被夹在框内**，拖不出框（防呆，防止压到缝线 / 拉链 / 翻盖外沿）
- logo 选中后显示虚线框 + 八个缩放控制点。拖动移动，四角控制点缩放（锁长宽比，Shift 自由拉伸）
- 右栏：宽 / 高（mm）、距框左沿 / 距框下沿（mm），实时联动；**色号**（选填，留空则工艺尺寸图上不标该行）；**存为方案**按钮

### 步骤 4 导出

尚未设计界面。输出三份文件到 `output/`，完成后打开文件夹。

**底部（方案条）**：每个方案一张缩略图，点缩略图切换，当前方案蓝框高亮，末尾一个虚线"+"新建。贯穿步骤 3、4。

## 5. 数据流

### 5.1 坐标系与单位

- 所有框与 logo 位置在 `project.json` 中以**图片像素坐标**存储，原点左上
- 同时**冗余存储换算后的毫米值**。三份交付物一律读毫米值，不再做二次换算——这是"三份同源"的实现保证
- 像素 → 毫米：`mm = px ÷ px_per_mm`

### 5.2 project.json schema

```json
{
  "project": "2026-09-03_客户A_双肩包",
  "inputs": {
    "bag_image": "input/bag.jpg",
    "logo_source": "input/logo.ai",
    "logo_svg": "input/logo.svg",
    "logo_preview": "input/logo_preview.png"
  },
  "calibration": {
    "product_frame": { "x": 120, "y": 60, "w": 900, "h": 1200 },
    "width_mm": 300.0,
    "height_mm": 450.0,
    "px_per_mm": 3.0
  },
  "frames": [
    { "id": "f1", "name": "翻盖可印区", "x": 200, "y": 300, "w": 600, "h": 400 }
  ],
  "schemes": [
    {
      "id": "A",
      "frame_id": "f1",
      "logo_px": { "x": 320, "y": 380, "w": 226, "h": 90 },
      "size_mm": { "w": 75.3, "h": 30.0 },
      "offset_mm": { "left": 40.0, "bottom": 20.0 },
      "color": "PANTONE 186 C"
    }
  ]
}
```

- `calibration`：步骤 2A 产出。`height_mm` 可选，缺失则为 `null`，此时不做高度提示
- `frames`：步骤 2B 产出，数组（默认一个）
- `schemes`：步骤 3 每点一次"存为方案"追加一条。`size_mm` / `offset_mm` 在摆放时实时算出并写入

### 5.3 生成链路

```
1 上传
   bag.jpg        → input/
   logo.ai        → input/
                  → Inkscape 转 SVG → input/logo.svg
                  → Inkscape 渲 PNG → input/logo_preview.png

2A 产品框
   拖框 + 输入宽度mm → px_per_mm → calibration

2B logo 框
   拖框（每边贴可见特征）+ 可选命名 → frames[]

3 摆放
   框内拖动缩放 → logo_px + size_mm + offset_mm + color → schemes[]

4 导出（遍历 schemes[]，逐条读毫米值）
   ├ 客户选款图  每方案合成一张 → 拼版 → output/selection.png
   │             合成方式：alpha 平铺叠加（S1 红线）
   ├ 工艺尺寸图  size_mm + color → SVG 文本模板 → Inkscape → spec.pdf/.svg
   └ 定位图      包图 + frames[] + schemes[].offset_mm + size_mm
                 → SVG 文本模板 → Inkscape → placement.pdf/.svg
```

**三份同源的落点**：三条分支读的是同一个 `schemes[i]` 对象里已经算好的毫米值，彼此之间不存在换算关系，因此不可能出现不一致。

## 6. 开放问题 — 已解决

### 6.1 定位基准区（原阻塞，2026-09-03 解决）

**原问题**：设计假设定位基准 = 包正面底边 + 中心线，实际生产按结构部件定位（翻盖在包身中间时按翻盖底边）。

**Joe 的判断**：包型虽多，但通常直接用包的边缘定位，能解决 90%。不应花大量资源维护包型规则，应找一个**万全通用**的办法——画框工具直接限定边界范围，logo 在范围内移动缩放。

**结论**：

1. **废弃语义定位区枚举模型**（翻盖 / 前袋 / 包身 + 6 种基准边 + 线型锚点），改用**通用自由画框**。
   - 成本对比：旧模型每加一种包型要加一条规则，且剩下 10% 永远补不完；新模型每加一种包型只需画个框，逻辑不变，覆盖 100%。
2. **线型锚点（缝线 / 织带 / 拉链）v1 不做。**
3. **框兼两个身份**
   - **安全区（约束）**：logo 被夹在框内，拖不出去，防止压到缝线 / 拉链 / 翻盖外沿
   - **尺寸基准（datum）**：尺寸链标"距框左沿 / 下沿 X mm"
4. **框带可选命名 / 备注字段**，保留"翻盖可印区"这类给包厂看的语义。
5. **尺寸链相对框边**，不相对包身包围盒（Joe 定）。
6. **硬约束（补齐的漏洞）**：框的每一条边必须落在包身**肉眼可辨的物理特征**上。
   - 若不加此约束会出现：包厂拿着定位图，在实物包上找不到这条虚线框的对应位置，尺寸链读得懂却量不出来。
   - 加上后自洽：**框边 = 可见边缘**，包厂从实物上能量到。
7. 由此推出 UI 需**放大精贴 / 边缘吸附辅助**，否则手工画框难以精确贴在缝线上。
8. **框不需要独立实物尺寸**，全图一个 `px_per_mm` 即够——尺寸链只标 logo 距框边的距离，不依赖框本身多大。

### 6.2 包身识别与比例尺（原阻塞，2026-09-03 解决）

**原问题**：图片尺寸 ≠ 实物尺寸（四周留白），需识别包的像素包围盒。

**结论：包身包围盒根本不需要。**

复核三份交付物后确认，无一处需要包的像素边界：客户选款图用整张图、工艺尺寸图与包图无关、定位图只需包图 + 框 + 尺寸链。因此**自动背景分割模块整个砍掉**，原 v0.1 为此预留的核心工作量归零。

连带效应：原 6.2 子问题「背景是纯白还是浅灰、有无阴影倒影」自动消失——只影响视觉观感，不影响标定。

**标定改为两步（Joe 提案）**：

| 子步 | 动作 | 产出 |
|------|------|------|
| 2A 产品框 | 拖矩形贴合包主体轮廓（提手不计），输入实物宽 / 高 mm | `px_per_mm` |
| 2B logo 框 | 拖矩形，每边贴可见物理特征，可命名 | 定位基准 + 安全区 |

**不能加物理参照物**（图由工厂 / 客户给）。改用产品框 + 宽度定标：

- **以宽度定标**（Joe 判断）：软包宽度由底围 / 定型决定，基本固定，可信度最高；高度受填充程度与塌陷影响，不可靠
- **高度为选填**，填了仅显示推算高与填入高的差值提示，不参与 `px_per_mm` 计算
- 原 v0.1 的「横纵双方向偏差 >2% 硬告警」**降级为黄色提示**，理由见 6.3

### 6.3 精度与透视（v0.2 新增分析）

**软包轮廓误差量级**：软包会塌会鼓、边缘为渐变阴影、提手是否计入含糊，轮廓判定误差约 ±2～5mm。对 300mm 的包即 **0.7%～1.7%**，传导到 50mm 的 logo 为 **±0.35～0.85mm**。

**判定：可接受，不阻塞。** 两个理由：
1. 该误差是**系统性**而非随机的——同一包型用同一框，误差方向一致，不会造成批次间不一致
2. 极端情况会被差值提示暴露

**为什么不保留 2% 硬告警**：该告警的前提是高度可信；既然高度本就不可信，它会把软包的正常高度偏差误报为错误。虚警几次后告警就没人信了，反而掩盖真实问题。

**黄色提示必须写清三种可能成因**，否则无法用于人工判断：
1. 软包高度塌陷 / 填充程度不同（正常，可忽略）
2. 产品框画得不准（需重画）
3. 拍摄存在透视，非等比例缩放（需换图或重拍）

**低成本缓解（不需加道具，可向工厂 / 客户提）**：
- 填充饱满
- 正对镜头
- 提手收拢
- 框定规则明示：只框主体，提手 / 肩带 / 织带不计

### 6.4 边界框为何不用 AI 视觉识别（v0.2 新增）

Joe 曾提出是否用 AI 识别界定边界框，或与 WorkBuddy / 千问办公联动。**结论：不上 AI。** 三理由：

1. **把"确定"换成"不确定"，且不确定性落在地基上。** `px_per_mm` 从框算出，框的不确定性直接污染全链路毫米数，违背"零换算误差"这一核心价值（S2）。
2. **这件事人做得比 AI 好且更快。** 鼠标一拖 2 秒；人眼对"包的边缘在哪"的判断远超 VLM 坐标回归精度。VLM 吐边界框的典型误差是像素级百分比，本场景要的是亚像素级**可复现**。
3. **依赖成本不划算，因为频率低。** 框按包型画一次而非按订单，包型复用时框也复用。网络 + API key + 延迟 + 费用，换来的只是省掉一次拖拽。

**与 S1 的关系**：边界框识别不重画效果图，字面不违反 S1，但精神一致——链上每个数字必须可复现、可追溯。

**与 WorkBuddy / 千问联动的正确位置**：不在识别边界框，而在订单侧自动化（从邮件 / 订单读客户名与 logo 附件 → 自动建项目文件夹并命名 → 导出后打包发工厂）。那省的是行政时间，不是设计判断。属 v2，v1 不做。

### 9.2 关键技术参数（供实现直接引用）

- **单位换算**：1 mm = 2.8346 pt
- **SVG 模板单位策略**：`viewBox` 数值 = mm 数值（1 user unit = 1 mm），`width`/`height` 写 `"115.30mm"`。转 PDF 后自动 1:1
- **转曲参数**：`--export-text-to-path`
- **DPI 无关性**：`--export-dpi` 对 mm 单位的 SVG 无影响（default/96/300 尺寸均正确），无需设置
- **无效参数**（勿用）：`--pdf-page=1` 在 1.4.4 不存在；`--export-ps-level=3` 对 EPS 导入无效
- **性能**：Pillow alpha 叠加 15.7ms，但 PNG 编码 133ms → **预览必须走前端 Canvas，后端 Pillow 仅用于导出**

### 9.3 兜底路径
