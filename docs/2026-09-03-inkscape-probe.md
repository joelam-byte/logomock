## 7. 补充：为什么 `.ai` 导出不了，以及能否解决

Joe 追问「为什么 .ai 无法导出？能否解决」，补查如下。

### 7.1 根因（三层）

**第一层：`.ai` 是 Adobe 专有格式，从未公开规范。**
对比之下，PDF 是 ISO 标准（ISO 32000）、EPS 是公开规范、SVG 是 W3C 标准——这些开源软件都能实现。`.ai` 没有规范文档，只能逆向工程。

**第二层：现代 `.ai` 的真实结构 = PDF + Adobe 私有数据块。**
Illustrator 保存时默认勾选 "Create PDF Compatible File"，文件里嵌入一份完整 PDF，另外附加 `AIPrivateData` 块（存放图层、画板、色板、AI 特有对象）。

这解释了一个看似矛盾的现象：**Inkscape 能读 `.ai` 却不能写 `.ai`**——读的时候它读的是里面那份 PDF；写则需要同时伪造私有块，而这部分没有规范。

实测佐证：把 `roundtrip.pdf` 改名为 `as_ai.ai` 后，Inkscape 依然能读回（1623 bytes），文件头为 `%PDF-1.5`。这**只证明结构等同 PDF，不证明 AI 会接受它**。

**第三层：开源社区主动放弃。**
Inkscape 早期（0.4x）曾有过 AI 输出，1.0 重构导出系统后只保留开放格式。原因：逆向专有格式有法律风险，维护成本高，而 PDF 已能满足绝大多数交付需求。

### 7.2 关键环境事实：本机已装 Adobe Illustrator

```
C:\Program Files\Adobe\Adobe Illustrator 2026\Support Files\Contents\Windows\Illustrator.exe
```

同机还装了：Illustrator 2024、Illustrator 2023、Photoshop 2026/2025/2023、Acrobat DC。

**这意味着「用 AI 自己把 PDF 转成真正的 .ai」这条路是通的**（Windows COM 自动化或 ExtendScript / JSX 脚本）。

### 7.3 三条解决路径对比

| 路径 | 做法 | 代价 | 评价 |
|------|------|------|------|
| **A. 交 PDF** | 不追求 `.ai` | 零 | **推荐**，理由见 7.4 |
| **B. AI 自动转** | COM/JSX 脚本让 AI 把 PDF 另存为 `.ai` | AI 启动 5～15 秒（串行阻塞）、脚本需实测、无人值守可能弹窗 | 技术可行但重，除非贴片厂硬性要求 `.ai` |
| **C. PDF 改名 `.ai`** | 直接改扩展名 | 零 | **不推荐**，理由见 7.5 |

### 7.4 为什么推荐交 PDF（这关系到「必须给 .ai」这个前提是否成立）

**PDF 是印前交付的国际标准，`.ai` 是工作文件格式。** 印刷厂 / 贴片厂的标准收件格式是 PDF/X-1a 或 PDF/X-4，不是 `.ai`。很多设计公司给工厂就交 PDF，`.ai` 只在设计师之间传工作文件时使用。

因此「必须给贴片厂 `.ai`」这个前提本身可能不成立。**建议拿 PDF 直接问贴片厂，大概率答复是能用。**

### 7.5 为什么不推荐改名

- 文件头是 `%PDF-1.5`，改名 `.ai` 是名不副实
- AI 可能因缺私有块报「文件损坏」
- 工厂若用 CorelDRAW / CAD / 排版软件打开，扩展名与真实格式不符会出问题
- 将来出质量问题时难以追溯——我们交付了一个伪装格式的文件

### 7.6 决策建议（按成本从低到高执行）

1. **用已装的 AI 2026 打开 `_probe/roundtrip.pdf`**，确认路径可编辑（约 1 分钟）
2. **同时拿这份 PDF 问贴片厂能否接收**
3. 若两者都通过 → 交 PDF，问题消失，无需任何额外开发
4. 若贴片厂坚持要 `.ai` → 再评估路径 B（AI 自动转）

### 7.7 已确认的相邻决策

- **EPS 输入不做处理**（Joe 2026-09-03 确认）：客户基本不给 EPS，不做检测也不做优雅降级
- **开发不因格式问题卡住**：验证与开发并行，架构按「格式可配置」设计

## 9. S2/S3 尺寸 1:1 保真实测（本项目最关键的验证）

探测脚本：`_probe/probe_svg_spec.py`

### 9.1 为什么这是最关键的验证

设计文档要求工艺尺寸图「1:1 矢量，打印可量」。但 **SVG 用 mm 绝对单位，PDF 内部用 point**（1pt = 1/72 inch = 0.352778mm）。若转换时单位映射错误，工厂拿尺子量出的尺寸就是错的，交付物直接作废——而且这种错误极隐蔽，不量不知道。

### 9.2 结果：完全通过

| 项 | 数值 |
|----|------|
| 期望页面尺寸 | 115.3000 × 95.0000 mm |
| PDF 实测尺寸 | 115.3000 × 95.0000 mm |
| **偏差** | **0.000003 / 0.000000 mm** |

换算关系：**1 mm = 2.8346 pt**（页面宽 115.30mm = 326.83 pt）

### 9.3 验证有效的 SVG 模板单位策略

```
viewBox 数值 = mm 数值，即 1 user unit = 1 mm
width/height 属性写 "115.30mm"
```

这样 SVG 内部所有坐标都能直接用毫米思考和书写，转 PDF 后自动 1:1。**这是"打印可量"的机制保证，实现时必须沿用。**

### 9.4 其他发现

| 项 | 结果 |
|----|------|
| 文字转曲 | ✅ PDF 内无字体引用，工厂缺字体也不会错版 |
| DPI 参数影响 | **无** —— default / 96 / 300 三种设置尺寸均正确，实现时无需设置 `--export-dpi` |
| **EPS 输出** | ❌ **BoundingBox 按内容边界算，不是页面** |

**EPS 问题详情**：页面 115.30 × 95.00 mm，但 EPS BoundingBox 只有 86.78 × 69.85 mm（偏差 28.5 / 25.2 mm）。EPS 规范中 BoundingBox 描述的是内容边界，不含页面留白。这与我们"1:1 打印可量"的语义不符，是砍掉 EPS 的第二条理由。

### 9.5 踩坑记录

**Inkscape 1.4 输出的 PDF 会把页面对象放进压缩的对象流（ObjStm）**，直接正则匹配原始字节找不到 `/MediaBox`，必须先解压 FlateDecode 流再解析。探测脚本已实现此逻辑，工程师可直接复用。

## 11. 实现阶段补充发现（2026-09-03 工程师实测）

### 11.1 Inkscape 按 `--export-filename` 扩展名识别输出格式

工程师在 B3 实现时踩到：convert 的临时文件最初命名为 `logo.svg.tmp`（`.tmp` 扩展名），导致 Inkscape 无法识别输出格式、转换失败。**改为 `logo.tmp.svg`（保留 `.svg` 扩展名）后成功。**

**含义**：凡是用 `--export-filename` 指定临时输出，临时文件必须保留目标格式的扩展名，成功后再 `os.replace` 到正式文件名。

### 11.2 退出码恒为 0 的 HTTP 层验证

端到端实测确认（主理人独立验证，未复用工程师测试）：
- 中文项目名上传 → `logo.svg` 正常生成（949 bytes）
- EPS 上传后转换 → 正确返回 `{"ok":false,"error":{"code":"INPUT_UNREADABLE","level":"block","stderr":"...parser error..."}}`，**非假成功**

### 11.3 中文项目名需 URL 编码（前端自动，无风险）

curl 直接传中文路径会得 400（curl 不编码），但浏览器自动 URL 编码，实测编码后中文项目名全链路正常。**前端无需特殊处理。**
